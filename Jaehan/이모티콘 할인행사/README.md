# 이모티콘 할인행사 문제 풀이 공유

[문제 링크](https://school.programmers.co.kr/learn/courses/30/lessons/150368)

## 1. 접근법과 단순 풀이의 한계

이모티콘마다 10, 20, 30, 40 중 하나의 할인율을 정해야 합니다. 각 사용자는 **자신이 원하는 비율 이상으로 할인하는 이모티콘을 전부 사고**, 그 총액이 자신의 기준 금액 이상이면 **구매를 취소하고 이모티콘 플러스에 가입**합니다. 목표는 1순위로 플러스 가입자 수, 2순위로 이모티콘 매출액을 최대화하는 것입니다.

- **매출을 기준으로 할인율을 고르는 그리디의 한계**: 두 목표는 서로 어긋납니다. 가입자가 한 명 늘어난다는 것은 곧 **그 사람의 구매액이 매출에서 통째로 빠진다**는 뜻이기 때문입니다. 입출력 예 #1에서 할인율을 `[40, 40]`으로 두면 매출이 19,200원까지 올라가지만 가입자는 0명이라, 가입자 1명에 매출 5,400원인 정답보다 **순위가 낮습니다.** 매출이라는 2순위 지표만 보고 고르면 1순위인 가입자 수를 놓칩니다.
- **무조건 최대 할인율을 주는 그리디의 한계**: 그렇다고 할인율을 전부 40으로 밀어도 안 됩니다. 입출력 예 #2에서 `[40, 40, 40, 40]`은 가입자가 3명뿐이지만, 정답인 `[40, 40, 20, 40]`은 세 번째 이모티콘의 할인율을 **오히려 낮춰서** 가입자를 4명으로 늘립니다. 할인율이 낮으면 그 이모티콘을 사는 사람이 줄어 오히려 기준 금액을 넘기지 못하게 되는 사용자가 생기는데, 이 효과가 사용자마다 다르게 나타나므로 **이모티콘 하나만 따로 떼어 최적 할인율을 정할 수 없습니다.**
- **할인율을 연속적인 값으로 보는 접근의 한계**: 1%부터 40%까지 자유롭게 정할 수 있다고 보면 경우의 수가 $40^7 \approx 1{,}638$억 가지가 되어 탐색 자체가 불가능합니다. 하지만 제한사항은 할인율을 **10, 20, 30, 40 네 가지로 못 박고** 있습니다.
- **방향 수정**: 네 가지 할인율에 이모티콘이 최대 7개이므로 조합은 $4^7 = 16{,}384$가지뿐입니다. 후보를 좁히려 하지 말고 **모든 할인율 조합을 만들어 완전탐색**하는 방식으로 접근을 정리했습니다.

## 2. 해결 코드

```python
from itertools import product

def solution(users, emoticons):
    ## 할인율은 10, 20, 30, 40 네 가지 중 하나만 가능하고 이모티콘은 최대 7개
    ## -> 할인율 조합은 최대 4^7 = 16,384가지뿐이므로 완전탐색
    ## 목표의 우선순위는 1) 플러스 가입자 수, 2) 이모티콘 매출액 순서다.
    ## 가입자가 늘면 그 사람의 구매는 취소되어 매출이 오히려 줄어들 수 있으므로
    ## 매출만 보고 고르는 그리디로는 답을 찾을 수 없다.

    answer = [0, 0]

    # 1. 이모티콘 개수만큼 할인율을 중복 조합으로 뽑아 모든 경우를 생성
    for rates in product([10, 20, 30, 40], repeat=len(emoticons)):

        plus = 0    # 이모티콘 플러스 가입자 수
        total = 0   # 이모티콘 매출액

        # 2. 각 사용자가 이 할인율 조합에서 어떻게 행동하는지 계산
        for want, limit in users:

            # 2-1. 원하는 비율 이상으로 할인하는 이모티콘은 모두 구매
            spent = 0
            for rate, price in zip(rates, emoticons):
                if rate >= want:
                    # 가격은 100의 배수, 할인율도 10의 배수라 항상 정수로 떨어짐
                    spent += price * (100 - rate) // 100

            # 2-2. 구매 비용이 기준 이상이면 구매를 취소하고 플러스에 가입
            if spent >= limit:
                plus += 1
            else:
                total += spent

        # 3. 가입자 수 -> 매출액 순으로 비교 (리스트 비교는 앞 원소부터 차례로 보므로 우선순위와 일치)
        if [plus, total] > answer:
            answer = [plus, total]

    return answer
```

## 3. 구현 전략 및 이유

### 후보를 좁히지 않고 모든 할인율 조합을 만드는 이유

제한사항이 탐색 크기를 이미 정해 줍니다. 이모티콘은 **최대 7개**, 할인율은 **10, 20, 30, 40 네 가지**이므로 조합은 $4^7 = 16{,}384$가지가 전부입니다. 사용자가 최대 100명, 이모티콘이 7개이니 전부 대조해도 약 1,150만 번이면 끝납니다.

`product([10, 20, 30, 40], repeat=len(emoticons))`는 **이모티콘마다 독립적으로** 네 개의 할인율 중 하나를 고르는 중복순열을 만듭니다. `combinations`가 아니라 `product`인 이유는 서로 다른 이모티콘이 같은 할인율을 가질 수 있고, 몇 번째 이모티콘에 어떤 할인율을 붙였는지가 결과를 바꾸기 때문입니다.

### 두 목표를 리스트 비교 하나로 처리하는 이유

문제의 목표는 **"가입자 수가 우선, 같으면 매출액"** 이라는 2단계 우선순위입니다. 파이썬의 리스트(와 튜플) 비교는 **앞 원소부터 차례로 비교하다가 승부가 나면 멈추는** 사전식 비교라 이 규칙과 정확히 일치합니다.

```python
[1, 5400] > [0, 19200]   # True: 매출이 3배 넘게 적어도 가입자가 많으면 이김
[2, 100] > [2, 90]       # True: 가입자가 같으면 매출로 판가름
```

가입자 수와 매출액을 따로 변수에 담고 `if plus > best_plus or (plus == best_plus and total > best_total)`처럼 쓸 수도 있지만, 조건이 길어지고 두 번째 비교를 빠뜨리기 쉽습니다. 리스트로 묶으면 우선순위가 **원소의 순서 그대로** 드러납니다.

### 할인가를 정수 나눗셈으로 계산하는 이유

제한사항에 **이모티콘 가격은 100의 배수**이고 할인율은 10의 배수이므로, `price * (100 - rate) // 100`은 항상 나머지 없이 떨어집니다. 실수 연산(`price * 0.9`)을 쓰면 부동소수점 오차로 기준 금액과의 비교(`spent >= limit`)가 어긋날 수 있어, 처음부터 정수로만 계산했습니다.

곱셈을 먼저 하고 나눗셈을 나중에 하는 순서도 중요합니다. `price // 100 * (100 - rate)`처럼 순서를 바꿔도 이 문제에서는 값이 같지만, 곱셈을 먼저 두면 가격이 100의 배수라는 조건에 기대지 않아도 오차가 생기지 않습니다.

### 시간 및 공간 복잡도

- **시간 복잡도**: $O(4^E \times U \times E)$ ($E$는 이모티콘 개수(최대 7), $U$는 사용자 수(최대 100)입니다. 최악의 경우 $16{,}384 \times 100 \times 7 \approx 1{,}150$만 번으로, 실제 측정 시 약 0.8초입니다.)
- **공간 복잡도**: $O(E)$ (`product`는 제너레이터라 16,384가지를 한꺼번에 메모리에 올리지 않고, 매 순회마다 길이 $E$짜리 튜플 하나만 사용합니다.)
