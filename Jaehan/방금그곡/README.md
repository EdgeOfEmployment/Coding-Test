# 방금그곡 문제 풀이 공유

[문제 링크](https://school.programmers.co.kr/learn/courses/30/lessons/17683)

## 1. 접근법과 단순 풀이의 한계

라디오에서 흘러나온 멜로디 `m`이 어느 곡의 일부인지 찾는 문제입니다. 곡은 **1분에 한 음씩** 재생되고, 악보가 재생 시간보다 짧으면 **처음부터 다시 반복**됩니다. 조건에 맞는 곡이 여러 개면 **재생된 시간이 가장 긴 곡**, 그래도 같으면 **먼저 입력된 곡**을, 하나도 없으면 `(None)`을 반환합니다.

- **악보 문자열을 그대로 `contains`로 비교하는 접근의 한계**: `C#`은 두 글자지만 **한 개의 음**입니다. 악보 `CC#BCC#BCC#B`에서 기억한 멜로디 `CB`를 그대로 찾으면, `C#`의 `C`와 바로 뒤의 `B`가 붙어 **있지도 않은 멜로디를 찾았다고 판정**합니다. 반대로 `C#B`를 찾을 때도 `C`와 `#B`의 경계가 보장되지 않아, 글자 단위 비교와 음 단위 비교가 어긋납니다.
- **악보를 그대로 두고 멜로디를 찾는 접근의 한계**: 재생 시간이 악보보다 길면 악보가 **순환해서 반복**되므로, `ABCDEFG`를 10분간 재생하면 실제로 들린 멜로디는 `ABCDEFGABC`입니다. 악보만 들고 찾으면 **끝과 처음이 이어지는 구간**인 `GA`나 `FGAB`를 놓칩니다. 그렇다고 악보를 두세 번 이어 붙이는 식으로 땜질하면, 재생 시간이 악보 길이의 몇 배인지에 따라 부족해집니다.
- **재생 시간이 악보보다 짧은 경우를 간과하는 접근의 한계**: 반대 방향의 함정도 있습니다. 악보가 `ABCDEFG`인데 3분만 재생됐다면 네오가 들을 수 있는 건 `ABC`뿐입니다. 악보 전체를 비교 대상으로 삼으면 **듣지도 않은 `DEFG` 구간에서 멜로디를 찾아내** 엉뚱한 곡을 답으로 내놓습니다.
- **방향 수정**: `#`이 붙은 음을 **한 글자 소문자로 치환**해 글자 수와 음의 개수를 일치시키고, 악보를 **재생 시간만큼 정확히 순환 확장**해 실제로 들린 멜로디를 만든 뒤 포함 여부를 확인하는 방식으로 접근을 정리했습니다. 확장 길이를 재생 시간에 맞추면 **길어서 반복되는 경우와 짧아서 잘리는 경우가 한 번에** 처리됩니다.

## 2. 해결 코드

```java
import java.util.*;

class Solution {
    public String solution(String m, String[] musicinfos) {
        // 음 : C, C#, D, D#, E, F, F#, G, G#, A, A#, B 12개
        // 각 음은 1분에 1개씩 재생되므로 악보길이를 알아야하며 구한 악보 길이로 반복된 멜로디를 구해야함
        // 1. 악보 길이가 실제 재생된 시간보다 짧을 때 -> 전체 멜로디를 다 알 수 있음
        // 2. 악보길이가 실제 재생된 시간보다 길 때 -> 네오가 알 수 있는 멜로디는 실제 재생된 시간만큼 잘린 길이
        
        String answer = "(None)";
        int maxPlayTime = -1; // 재생 시간이 가장 긴 음악을 찾기 위한 변수

        // 멜로디 m의 #음들을 한 글자 소문자로 치환
        m = replaceNote(m);

        for (String music : musicinfos) {
            String[] info = music.split(",");
            int playTime = changeToMin(info[0], info[1]); // 총 재생시간
            String songName = info[2];                     // 곡 이름
            String melody = replaceNote(info[3]);          // 악보 (#음 치환 적용)

            // 악보를 재생 시간(playTime)만큼 순환 반복(확장)하여 실제 재생된 멜로디 생성
            StringBuilder totalMelody = new StringBuilder();
            for (int i = 0; i < playTime; i++) {
                totalMelody.append(melody.charAt(i % melody.length()));
            }

            // 기억한 멜로디가 실제 재생된 멜로디에 포함되어 있는지 확인
            if (totalMelody.toString().contains(m)) {
                // 재생 시간이 더 긴 음악 우선 (시간이 같으면 먼저 입력된 음악 유지)
                if (playTime > maxPlayTime) {
                    maxPlayTime = playTime;
                    answer = songName;
                }
            }
        }

        return answer;
    }

    // 실제 재생된 시간을 분으로 변환하여 최종 재생시간을 반환할 함수
    private int changeToMin(String time1, String time2) {
        String startHour = time1.split(":")[0];
        String startMin = time1.split(":")[1];

        String endHour = time2.split(":")[0];
        String endMin = time2.split(":")[1];

        int startHourInt = Integer.parseInt(startHour) * 60;
        int startMinInt = Integer.parseInt(startMin);
        int totalStart = startHourInt + startMinInt;

        int endHourInt = Integer.parseInt(endHour) * 60;
        int endMinInt = Integer.parseInt(endMin);
        int totalEnd = endHourInt + endMinInt;

        return totalEnd - totalStart;
    }

    // #이 붙은 2글자 음을 1글자 소문자로 변환하는 함수
    private String replaceNote(String str) {
        return str.replace("C#", "c")
                  .replace("D#", "d")
                  .replace("F#", "f")
                  .replace("G#", "g")
                  .replace("A#", "a")
                  .replace("B#", "b");
    }
}
```

## 3. 구현 전략 및 이유

### `#`이 붙은 음을 한 글자 소문자로 치환하는 이유

이 문제의 핵심 함정은 **"한 음"과 "한 글자"가 어긋난다**는 점입니다. `C#`은 1분을 차지하는 한 개의 음인데 문자열에서는 두 글자입니다. 그래서 재생 시간만큼 글자를 세는 계산도, 멜로디 포함 여부를 보는 비교도 모두 틀어집니다.

`C#`을 `c`로 바꾸면 **글자 하나가 정확히 음 하나**가 되어 두 문제가 동시에 풀립니다. 소문자를 고른 것도 의도한 선택입니다. 원래 악보에는 대문자 `A`~`G`만 나오므로, 소문자로 바꾼 반음은 **기존 음과 절대 충돌하지 않습니다.** 치환 후에는 `charAt(i)` 하나가 `i`번째 분에 재생된 음이 되고, `contains`도 음 단위 비교와 정확히 일치합니다.

기억한 멜로디 `m`과 악보 양쪽에 **같은 치환**을 적용하는 것도 필수입니다. 한쪽만 바꾸면 `c`와 `C#`을 비교하게 되어 아무것도 찾지 못합니다. `m`은 반복문 바깥에서 한 번만 치환해 곡마다 같은 작업을 되풀이하지 않도록 했습니다.

참고로 `B#`은 문제에 주어진 12개 음에 들어 있지 않아 실제로 치환될 일이 없습니다. 다른 반음들과 형태를 맞춰 적어 둔 것이며, 결과에는 영향을 주지 않습니다.

### 악보를 재생 시간만큼 순환 확장하는 이유

`i % melody.length()`는 악보의 끝에 도달하면 인덱스를 **0으로 되돌려** 처음부터 다시 읽게 합니다. 이 한 줄이 서로 반대처럼 보이는 두 경우를 한꺼번에 처리합니다.

- **재생 시간 > 악보 길이**: 악보가 반복되며 `playTime` 길이까지 채워집니다. 끝과 처음이 이어지는 구간(`...GAB...`)도 자연스럽게 만들어져 **경계를 넘는 멜로디**를 놓치지 않습니다.
- **재생 시간 < 악보 길이**: 반복문이 `playTime`번만 돌기 때문에 악보가 **그 길이에서 잘립니다.** 들리지 않은 뒷부분이 비교 대상에 들어오지 않습니다.

경우를 나눠 `if`로 분기하거나 "악보를 몇 번 이어 붙일지"를 따로 계산할 수도 있지만, **최종 멜로디의 길이는 결국 `playTime`** 하나로 결정됩니다. 그 사실을 반복 횟수에 그대로 반영하면 분기가 사라집니다.

문자열을 `+=`로 이어 붙이면 Java의 `String`은 불변이라 **매번 새 객체를 만들어** 길이에 비례하는 복사가 누적됩니다. `StringBuilder`는 내부 버퍼에 덧붙이므로 `append` 한 번이 상수 시간에 가깝게 끝납니다.

### 시각을 분으로 환산해 뺄셈 한 번으로 처리하는 이유

재생 시간은 `시:분` 두 개의 단위로 주어지지만, 음은 **1분에 하나씩** 재생되므로 필요한 값은 **분 단위 길이 하나**입니다. 시와 분을 각각 빼면 분이 음수가 될 때 자리 빌림을 처리해야 하지만(`00:55`~`01:10`), `시 × 60 + 분`으로 **단일 숫자로 환산**해 두면 뺄셈 한 번으로 끝납니다. 자리 빌림 분기가 아예 생기지 않습니다.

### 우선순위를 비교 하나로 처리하는 이유

답을 고르는 규칙은 **"재생 시간이 긴 곡 우선, 같으면 먼저 입력된 곡"** 입니다. 코드는 `playTime > maxPlayTime`이라는 **등호 없는 비교** 하나로 이 두 규칙을 모두 만족시킵니다. 곡을 입력 순서대로 순회하므로, 재생 시간이 같은 곡이 나중에 나와도 조건이 거짓이 되어 **먼저 찾은 곡이 그대로 유지**되기 때문입니다. `>=`로 바꾸면 동점일 때 나중 곡으로 덮어써져 규칙을 위반합니다.

`maxPlayTime`을 `-1`로, `answer`를 `(None)`으로 초기화한 것도 같은 맥락입니다. 재생 시간은 항상 0 이상이므로 **첫 번째로 조건을 만족한 곡은 무조건 갱신**에 성공하고, 끝까지 아무 곡도 걸리지 않으면 초기값 `(None)`이 그대로 반환됩니다. "찾지 못한 경우"를 위한 별도의 분기가 필요하지 않습니다.

### 시간 및 공간 복잡도

- **시간 복잡도**: $O(S \times P \times M)$ ($S$는 곡의 개수, $P$는 곡의 재생 시간(분), $M$은 기억한 멜로디의 길이입니다. 곡마다 길이 $P$의 멜로디를 만드는 데 $O(P)$, 여기서 `contains`로 멜로디를 찾는 데 최악의 경우 $O(P \times M)$이 듭니다. 시각이 `00:00`~`23:59` 범위이므로 $P$는 1,440 미만으로 묶여 있습니다.)
- **공간 복잡도**: $O(P)$ (곡 하나를 처리할 때 확장한 멜로디를 담는 `StringBuilder`가 가장 큰 공간이고, 다음 곡으로 넘어가면 교체되므로 모든 곡의 멜로디를 동시에 들고 있지 않습니다.)
