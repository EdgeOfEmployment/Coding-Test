# 광물 캐기 문제 풀이 공유

[문제 링크](https://school.programmers.co.kr/learn/courses/30/lessons/172927)

## 1. 접근법과 단순 풀이의 한계

다이아몬드/철/돌 곡괭이를 각각 몇 개씩 가지고 있고, 광물은 **주어진 순서대로만** 캘 수 있습니다. 곡괭이를 한 번 들면 **광물 5개를 캘 때까지 바꿀 수 없고**, 곡괭이와 광물의 조합에 따라 피로도가 1, 5, 25로 달라집니다. 모든 광물을 캐거나 곡괭이를 다 쓸 때까지 캤을 때의 **최소 피로도**를 구하는 문제입니다.

- **광물 하나씩 보며 곡괭이를 고르는 접근의 한계**: "이 광물은 다이아니까 다이아 곡괭이로"라는 선택은 **애초에 불가능**합니다. 곡괭이를 들면 5개를 연속으로 캐야 하므로, 판단 단위는 광물 하나가 아니라 **광물 5개 묶음**입니다.
- **앞 묶음부터 강한 곡괭이를 쓰는 그리디의 한계**: 곡괭이를 **어떤 순서로 들지는 자유**인데, 앞에서부터 좋은 것을 소모하면 뒤에 오는 어려운 묶음에 약한 곡괭이만 남습니다. `picks = [1, 1, 0]`, `minerals = ["stone"] * 5 + ["diamond"] * 5`인 경우, 앞에서부터 쓰면 다이아 곡괭이로 돌 5개(피로도 5) → 철 곡괭이로 다이아 5개(피로도 25)라 **30**이 되지만, 순서를 뒤집으면 **10**으로 끝납니다.
- **남은 광물 전체의 다이아 개수를 세는 그리디의 한계**: 전체에 다이아가 몇 개인지가 아니라 **어느 묶음에 몰려 있는지**가 비용을 결정합니다. 다이아 5개가 한 묶음에 뭉쳐 있으면 곡괭이 하나로 막을 수 있지만, 다섯 묶음에 하나씩 흩어져 있으면 다섯 개가 필요합니다. 총합만으로는 이 차이를 구분할 수 없습니다.
- **곡괭이 사용 순서를 완전탐색하는 접근의 한계**: 곡괭이는 최대 15개이므로 사용 순서는 $\frac{15!}{5!\,5!\,5!} = 756{,}756$가지이고, 각 경우마다 광물 75개를 훑으면 약 **5,700만 번**이라 파이썬에서는 시간이 위험합니다. 게다가 **같은 종류의 곡괭이는 서로 구분되지 않으므로** 이 탐색은 대부분 중복 계산입니다.
- **방향 수정**: 광물 순서가 고정이고 곡괭이마다 정확히 5개씩 캐므로, **묶음의 경계는 곡괭이를 어떤 순서로 쓰든 0~4번, 5~9번, ... 으로 이미 정해져 있습니다.** 남은 자유도는 **"어느 묶음에 어느 곡괭이를 줄 것인가"** 하나뿐이고, 이는 순서 탐색이 아니라 **정렬 후 짝지어 주기**로 풀립니다.

## 2. 해결 코드

```python
def solution(picks, minerals):
    ## 피로도는 5의 제곱수, 다이아몬드 > 철 > 돌
    ## 각 곡괭이는 종류에 무관하게 5회까지 사용 가능
    ## 곡괭이 사용 시 다 쓸 때까지 사용해야함
    ## 광물은 주어진 순서대로만 캘 수 있음
    ## 모든 광물을 다 캐거나, 곡괭이를 더 못 쓸 때까지 광물을 캠
    ## 한 번 시작한 작업에서 최소한의 피로도를 만족 -> 그리디 같아 보임
    ## 현재 남아있는 가장 강력한 곡괭이로, 지금 처리해야 할 가장 '부하가 큰(피로도가 많이 쌓이는) 5개 묶음'을 처리한다"는 매 순간의 선택이 전체 피로도를 최소화하는 최적의 선택

    answer = 0

    # 1. 슬라이싱 (곡괭이를 다 사용하는 횟수 기준)
    total_picks = sum(picks)
    max_mineral_cnt = total_picks * 5

    if len(minerals) > max_mineral_cnt:
        minerals = minerals[:max_mineral_cnt]

    # 2. 5개씩 묶기
    bundles = []
    for i in range(0, len(minerals), 5):
        bundle = minerals[i:i+5]
        dia = bundle.count("diamond")
        iron = bundle.count("iron")
        stone = bundle.count("stone")
        bundles.append((dia, iron, stone)) # 각 묶음별 광물 수

    bundles.sort(key = lambda x : (x[0], x[1], x[2]), reverse=True) # 내림차순 정렬 (다이아 > 철 > 돌 순서)

    # 3. 정렬된 묶음에 대해 피로도 연산 수행
    for dia, iron, stone in bundles:
        if picks[0] > 0:
            picks[0] -= 1
            answer += (dia + iron + stone)
        elif picks[1] > 0:
            picks[1] -= 1
            answer += (dia * 5 + iron + stone)
        else:
            picks[2] -= 1
            answer += (dia * 25 + iron * 5 + stone)

    return answer
```

## 3. 구현 전략 및 이유

### 광물을 5개 묶음으로 잘라 개수만 세는 이유

한 곡괭이는 정확히 광물 5개를 캡니다. 광물 순서가 고정이므로 **0~4번, 5~9번, 10~14번 ... 이라는 경계는 곡괭이를 어떤 순서로 들든 절대 바뀌지 않습니다.**

그리고 한 묶음의 피로도는 **그 안에 다이아/철/돌이 몇 개씩 있는지**로만 결정됩니다. 묶음 안에서 어떤 순서로 놓여 있든 합은 같으므로, `["diamond", "stone", "iron", "stone", "stone"]`을 통째로 들고 다닐 필요 없이 `(1, 1, 3)`이라는 **개수 세 개로 압축**할 수 있습니다. 비교와 정렬 대상이 문자열 리스트에서 정수 튜플로 바뀌어 이후 처리가 단순해집니다.

마지막 묶음만 5개 미만일 수 있는데, `range(0, len(minerals), 5)`와 슬라이싱은 남은 개수만큼만 잘라 주므로 별도 분기가 필요 없습니다.

### 묶음을 `(다이아, 철, 돌)` 내림차순으로 정렬하는 이유

**"이 묶음이 얼마나 부담스러운가"의 순서가 곡괭이 종류와 무관하게 동일하기** 때문입니다. 묶음 크기가 5로 같을 때, 다이아 $d$개·철 $i$개·돌 $s$개($d + i + s = 5$)인 묶음의 피로도는 이렇게 정리됩니다.

- **다이아 곡괭이**: $d + i + s = 5$ → 어떤 묶음이든 **항상 5로 같습니다.**
- **철 곡괭이**: $5d + i + s = 4d + 5$ → **다이아 개수만으로** 결정됩니다.
- **돌 곡괭이**: $25d + 5i + s = 24d + 4i + 5$ → **다이아가 1순위, 철이 2순위**입니다.

돌 곡괭이 식에서 다이아 하나 차이는 $24$를 만드는데, 철 개수 차이는 최대 $4 \times 5 = 20$이라 **다이아 차이를 뒤집지 못합니다.** 그래서 다이아 개수로 먼저 비교하고, 같을 때만 철 개수로 비교하는 **사전식 내림차순**이 곧 "피로도가 많이 쌓이는 순서"가 됩니다.

세 번째 키인 돌은 크기가 5인 묶음끼리는 앞 두 키가 같으면 자동으로 같아져 영향이 없지만, **5개 미만인 마지막 묶음**을 뒤로 밀어 주는 역할을 합니다. 광물 수가 적은 묶음은 그만큼 싸므로 약한 곡괭이에 넘기는 것이 맞습니다.

### 강한 곡괭이부터 차례로 배정하는 이유

정렬된 묶음에 다이아 → 철 → 돌 순으로 곡괭이를 나눠 주는 부분은 **교환 논법**으로 확인할 수 있습니다. 더 비싼 묶음 A에 약한 곡괭이를, 더 싼 묶음 B에 강한 곡괭이를 준 배정이 있다면, 둘을 맞바꿔도 손해가 없습니다. 위 식에서 **강한 곡괭이로 바꿨을 때 줄어드는 피로도는 다이아·철 개수가 많을수록 크기** 때문에, 아낀 양이 잃은 양보다 항상 크거나 같습니다.

즉 **"가장 비싼 묶음에 가장 강한 곡괭이"** 라는 짝짓기가 최적이고, 이는 정렬된 묶음 리스트를 앞에서부터 훑으며 `picks[0] → picks[1] → picks[2]` 순으로 소진하는 것과 같습니다. 곡괭이 사용 **순서**를 탐색할 필요가 없었던 이유도 여기에 있습니다. 실제로 캐는 순서는 광물 순서를 따르지만, **피로도 총합은 어느 곡괭이가 어느 묶음을 맡았는지에만** 의존합니다.

### 광물을 미리 잘라내는 이유

문제는 "모든 광물을 캐거나 **곡괭이를 더 쓸 수 없을 때까지**" 캔다고 명시합니다. 곡괭이가 `sum(picks)`개면 캘 수 있는 광물은 최대 `sum(picks) * 5`개이고, **그 뒤의 광물은 존재하지 않는 것과 같습니다.**

이 슬라이싱은 불필요한 계산을 줄이는 최적화이자 **마지막 `else` 분기를 안전하게 만드는 장치**이기도 합니다. 잘라낸 뒤에는 묶음 개수가 `sum(picks)` 이하임이 보장되므로, 다이아와 철 곡괭이가 모두 떨어진 시점에 반드시 돌 곡괭이가 남아 있습니다. `picks[2]`가 음수로 내려갈 일이 없어 별도의 종료 조건을 두지 않았습니다.

다만 이 코드는 `picks`를 직접 차감하므로 **호출자의 리스트가 변형됩니다.** 채점 환경에서는 문제가 없지만, 같은 `picks`를 재사용해야 한다면 `picks = picks[:]`로 복사해 두는 편이 안전합니다.

### 시간 및 공간 복잡도

- **시간 복잡도**: $O(m + b \log b)$ ($m$은 광물 수(최대 1,000), $b$는 묶음 수로 $\lceil m/5 \rceil \le 200$입니다. 광물을 한 번 훑어 묶음을 만드는 데 $O(m)$, 묶음 정렬에 $O(b \log b)$, 배정에 $O(b)$가 들어 실질적으로 $O(m)$에 가깝습니다.)
- **공간 복잡도**: $O(b)$ (묶음마다 정수 3개짜리 튜플 하나만 저장하므로 최대 200개입니다. 슬라이싱으로 만든 `minerals` 사본도 곡괭이 수에 비례해 최대 75개로 제한됩니다.)
