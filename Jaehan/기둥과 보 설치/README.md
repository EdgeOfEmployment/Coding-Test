# 기둥과 보 설치 문제 풀이 공유

[문제 링크](https://school.programmers.co.kr/learn/courses/30/lessons/60061)

## 1. 접근법과 단순 풀이의 한계

$n \times n$ 격자 벽면에 기둥과 보를 설치하거나 삭제하는 명령 `[x, y, a, b]`가 순서대로 주어집니다. 구조물은 다음 규칙을 항상 만족해야 하고, 규칙을 깨는 명령은 **무시**합니다. 모든 명령을 처리한 뒤 남은 구조물을 정렬해 반환하는 문제입니다.

- 기둥은 **바닥 위**에 있거나, **보의 한쪽 끝 위**에 있거나, **다른 기둥 위**에 있어야 합니다.
- 보는 **한쪽 끝이 기둥 위**에 있거나, **양쪽 끝이 다른 보와 동시에 연결**되어 있어야 합니다.

설치는 비교적 단순합니다. 새로 놓을 구조물 하나의 **주변 좌표만** 보면 규칙을 만족하는지 바로 알 수 있습니다. 어려운 쪽은 **삭제**입니다.

- **삭제할 구조물에 기대고 있는 주변만 골라서 검사하는 접근의 한계**: 처음에는 설치처럼 "삭제한 뒤 좌우 좌표의 구조물이 여전히 규칙을 만족하는지"를 직접 따져보려 했습니다. 그런데 무엇이 무엇에 기대고 있는지가 경우마다 다릅니다. 기둥 하나를 지우면 **그 위의 기둥**, 기둥 꼭대기에 걸린 **왼쪽 보와 오른쪽 보**가 영향을 받고, 보 하나를 지우면 **양 끝 위의 기둥**과 **좌우로 이어진 보**가 영향을 받습니다. 게다가 영향받는 보가 "양쪽 보에 걸쳐 있던" 경우인지 "기둥 위에 있던" 경우인지에 따라 다시 갈립니다. 경우를 손으로 나열하다 보면 하나만 빠뜨려도 틀리고, 좌표가 $x-1$, $x+1$, $y+1$로 흩어져서 헷갈리기 쉽습니다.
- **방향 수정**: 삭제를 "무엇이 영향받는지 계산"하는 문제로 보지 않고, **일단 지워 본 뒤 남아 있는 모든 구조물이 설치 규칙을 여전히 만족하는지 다시 확인**하는 문제로 바꿨습니다. 하나라도 깨지면 지운 것을 되돌립니다. 이렇게 하면 삭제 판정에 **설치 판정 함수를 그대로 재사용**할 수 있어서, 삭제 전용 경우의 수를 따로 만들 필요가 사라집니다.

## 2. 해결 코드

```java
import java.util.*;

class Solution {
    
    // 기둥과 보 구조물 상태를 저장할 배열 또는 집합
    // 여기서는 3차원 배열을 사용하여 [x][y][종류]로 표현 (0: 기둥, 1: 보)
    boolean[][] pillar;
    boolean[][] bo;

    public int[][] solution(int n, int[][] build_frame) {
        // 규칙
        // 기둥은 바닥 위에 있거나 보의 한쪽 끝 부분 위에 있거나, 또는 다른 기둥 위에 있어야 합니다. --> 기둥이 보 중간에 오는 경우는 없음
        // 보는 한쪽 끝 부분이 기둥 위에 있거나, 또는 양쪽 끝 부분이 다른 보와 동시에 연결되어 있어야 합니다.
        // 설치 시 가능 여부는 설치 전 좌우 좌표를 체크해야함
        // 삭제 시 가능 여부를 판단하기 위해선 해당 좌표에 대한 삭제 연산 후 좌우 좌표의 연산 결과가 규칙에 유효한지 체크해야함
        
        // [x,y,a,b] => [가로 좌표, 세로 좌표, (0 = 기둥, 1 = 보), (0 = 삭제, 1 = 설치)]
        // return => [x,y,a] 형태
        // -> x좌표 기준으로 오름차순 정렬하며, x좌표가 같을 경우 y좌표 기준으로 오름차순 정렬 + x, y좌표가 모두 같은 경우 기둥이 보보다 앞에 위치
        
        pillar = new boolean[n + 3][n + 3];
        bo = new boolean[n + 3][n + 3];

        for (int[] frame : build_frame) {
            int x = frame[0];
            int y = frame[1];
            int a = frame[2]; // a: 0(기둥), 1(보)
            int b = frame[3]; // b: 0(삭제), 1(설치)

            if (b == 1) { // 설치
                if (a == 0) { // 기둥 설치
                    if (canInstallPillar(x, y)) {
                        pillar[x][y] = true;
                    }
                } else { // 보 설치
                    if (canInstallBo(x, y)) {
                        bo[x][y] = true;
                    }
                }
            } else { // 삭제
                if (a == 0) { // 기둥 삭제
                    pillar[x][y] = false; // 일단 삭제해 봄
                    if (!isValid(n)) {
                        pillar[x][y] = true; // 불가능하면 원상복구
                    }
                } else { // 보 삭제
                    bo[x][y] = false; // 일단 삭제해 봄
                    if (!isValid(n)) {
                        bo[x][y] = true; // 불가능하면 원상복구
                    }
                }
            }
        }

        // 결과 리스트 생성
        List<int[]> resultList = new ArrayList<>();
        for (int x = 0; x <= n; x++) {
            for (int y = 0; y <= n; y++) {
                if (pillar[x][y]) resultList.add(new int[]{x, y, 0});
                if (bo[x][y]) resultList.add(new int[]{x, y, 1});
            }
        }

        // 정렬 조건 적용: x 오름차순, y 오름차순, 구조물 종류(기둥 0, 보 1) 오름차순
        resultList.sort((o1, o2) -> {
            if (o1[0] != o2[0]) return Integer.compare(o1[0], o2[0]);
            if (o1[1] != o2[1]) return Integer.compare(o1[1], o2[1]);
            return Integer.compare(o1[2], o2[2]);
        });

        int[][] answer = new int[resultList.size()][3];
        for (int i = 0; i < resultList.size(); i++) {
            answer[i] = resultList.get(i);
        }

        return answer;
    }

    // 기둥 설치 가능 여부 확인
    private boolean canInstallPillar(int x, int y) {
        // 1. 바닥 위인 경우 (y == 0)
        if (y == 0) return true;
        // 2. 다른 기둥 위인 경우
        if (y > 0 && pillar[x][y - 1]) return true;
        // 3. 보의 한쪽 끝 부분 위인 경우 (왼쪽 보가 있거나, 바로 아래에 보가 있는 경우)
        if ((x > 0 && bo[x - 1][y]) || bo[x][y]) return true;
        return false;
    }

    // 보 설치 가능 여부 확인
    private boolean canInstallBo(int x, int y) {
        // 1. 한쪽 끝 부분이 기둥 위에 있는 경우 (아래에 기둥이 있거나, 오른쪽 아래에 기둥이 있는 경우)
        if ((y > 0 && pillar[x][y - 1]) || (y > 0 && pillar[x + 1][y - 1])) return true;
        // 2. 양쪽 끝 부분이 다른 보와 동시에 연결되어 있는 경우
        if (x > 0 && bo[x - 1][y] && bo[x + 1][y]) return true;
        return false;
    }

    // 전체 구조물이 규칙을 만족하는지 검사
    private boolean isValid(int n) {
        for (int x = 0; x <= n; x++) {
            for (int y = 0; y <= n; y++) {
                if (pillar[x][y] && !canInstallPillar(x, y)) return false;
                if (bo[x][y] && !canInstallBo(x, y)) return false;
            }
        }
        return true;
    }
}
```

## 3. 구현 전략 및 이유

### 좌표 한 점에 기둥과 보를 따로 저장하는 이유

한 좌표 $(x, y)$에는 **기둥과 보가 동시에** 있을 수 있습니다. 기둥은 $(x, y)$에서 위로 $(x, y+1)$까지, 보는 $(x, y)$에서 오른쪽으로 $(x+1, y)$까지 뻗기 때문에 시작점이 같아도 서로 다른 구조물입니다. 그래서 `pillar[x][y]`와 `bo[x][y]` 두 배열로 나눠 저장했습니다.

이 기준을 잡아 두면 규칙이 배열 조회 몇 개로 바로 옮겨집니다.

| 판정 | 조건 | 코드 |
| --- | --- | --- |
| 기둥 | 바닥 위 | `y == 0` |
| 기둥 | 다른 기둥 위 | `pillar[x][y - 1]` |
| 기둥 | 보의 오른쪽 끝 위 | `bo[x - 1][y]` |
| 기둥 | 보의 왼쪽 끝 위 | `bo[x][y]` |
| 보 | 왼쪽 끝이 기둥 위 | `pillar[x][y - 1]` |
| 보 | 오른쪽 끝이 기둥 위 | `pillar[x + 1][y - 1]` |
| 보 | 양쪽 끝이 다른 보와 연결 | `bo[x - 1][y] && bo[x + 1][y]` |

배열 크기를 `n + 3`으로 넉넉하게 잡은 이유도 여기 있습니다. `x = n` 근처에서 `x + 1`을 조회해도 **범위를 벗어나지 않게** 해서, 경계 검사 조건을 따로 붙이지 않아도 됩니다. `x - 1`, `y - 1`처럼 음수가 될 수 있는 쪽만 `x > 0`, `y > 0`으로 막았습니다.

### 삭제를 "지워 보고 전체 검사 후 되돌리기"로 처리하는 이유

이 문제에서 가장 까다로웠던 부분입니다. 핵심은 **삭제 가능 여부와 설치 가능 여부가 같은 규칙**이라는 점입니다. 구조물을 하나 지웠을 때 문제가 되는 건 "남은 구조물 중 누군가가 더 이상 규칙을 만족하지 못하는 상황"뿐이고, 남은 구조물이 규칙을 만족하는지는 **설치할 때 쓰던 `canInstallPillar`, `canInstallBo`로 그대로 확인**할 수 있습니다.

그래서 삭제 명령이 오면 다음 순서로 처리합니다.

1. 해당 구조물을 `false`로 **먼저 지웁니다.**
2. `isValid`로 남아 있는 **모든** 기둥과 보가 설치 조건을 만족하는지 확인합니다.
3. 하나라도 만족하지 못하면 다시 `true`로 **원상복구**합니다.

"어떤 구조물이 영향받는가"를 사람이 미리 골라내지 않으므로 **빠뜨리는 경우가 생길 수 없습니다.** 기둥을 지웠을 때 그 위의 기둥이 무너지는지, 양옆 보가 버티는지, 보를 지웠을 때 옆 보가 다른 보에 걸쳐 버티는지 같은 경우가 전부 같은 검사 안에 들어갑니다.

전체를 다 훑는 게 비효율적으로 보이지만, $n \le 100$이라 한 번 검사가 약 $10^4$번이고 명령이 최대 $1{,}000$개이므로 최악이어도 $10^7$번 수준에 그칩니다. 영향받는 주변 좌표만 골라 검사하는 최적화도 가능하지만, 그 경우의 수를 정확히 나열하는 것 자체가 처음 접근에서 부딪힌 어려움이었기 때문에 **정확성을 확실히 보장하는 쪽**을 택했습니다.

### 결과를 좌표 순서대로 모으는 이유

반환 형식은 **x 오름차순 → y 오름차순 → 기둥이 보보다 앞**입니다. 결과를 모을 때 `x`를 바깥 반복, `y`를 안쪽 반복으로 돌고, 같은 좌표에서 기둥을 보보다 먼저 넣기 때문에 **수집 순서 자체가 이미 정렬 조건과 같습니다.** 코드의 `sort`는 이 순서를 명시적으로 보장하는 안전장치 역할이며, 빠져도 결과는 같습니다.

### 시간 및 공간 복잡도

- **시간 복잡도**: $O(F \times n^2)$ ($F$는 명령의 개수, $n$은 벽면 크기입니다. 설치는 $O(1)$이지만 삭제마다 `isValid`가 격자 전체를 $O(n^2)$로 훑습니다. 최종 결과 수집과 정렬은 $O(n^2 \log n)$으로 이보다 작습니다.)
- **공간 복잡도**: $O(n^2)$ (기둥과 보 상태를 담는 두 2차원 배열과 결과 리스트가 차지합니다.)
