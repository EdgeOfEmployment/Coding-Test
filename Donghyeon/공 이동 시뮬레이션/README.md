### 문제 설명

<p><code>n</code>행 <code>m</code>열의 격자가 있습니다. 격자의 각 행은 0, 1, ..., <code>n-1</code>번의 번호, 그리고 각 열은 0, 1, ..., <code>m-1</code>번의 번호가 순서대로 매겨져 있습니다. 당신은 이 격자에 공을 하나 두고, 그 공에 다음과 같은 쿼리들을 날리고자 합니다.</p>

<ul>
<li>열 번호가 감소하는 방향으로 <code>dx</code>칸 이동하는 쿼리 (<code>query(0, dx)</code>)</li>
<li>열 번호가 증가하는 방향으로 <code>dx</code>칸 이동하는 쿼리 (<code>query(1, dx)</code>)</li>
<li>행 번호가 감소하는 방향으로 <code>dx</code>칸 이동하는 쿼리 (<code>query(2, dx)</code>)</li>
<li>행 번호가 증가하는 방향으로 <code>dx</code>칸 이동하는 쿼리 (<code>query(3, dx)</code>)</li>
</ul>

<p>단, 공은 격자 바깥으로 이동할 수 없으며, 목적지가 격자 바깥인 경우 공은 이동하다가 더 이상 이동할 수 없을 때 멈추게 됩니다. 예를 들어, 5행 × 4열 크기의 격자 내의 공이 3행 2열에 있을 때 <code>query(3, 10)</code> 쿼리를 받은 경우 공은 4행 2열에서 멈추게 됩니다. (격자의 크기가 5행 × 4열이므로, 0~4번 행과 0~3번 열로 격자가 구성되기 때문입니다.)</p>

<p>격자의 행의 개수 <code>n</code>, 열의 개수 <code>m</code>, 정수 <code>x</code>와 <code>y</code>, 그리고 쿼리들의 목록을 나타내는 2차원 정수 배열 <code>queries</code>가 매개변수로 주어집니다. <code>n × m</code>개의 가능한 시작점에 대해서 해당 시작점에 공을 두고 <code>queries</code> 내의 쿼리들을 순서대로 시뮬레이션했을 때, <code>x</code>행 <code>y</code>열에 도착하는 시작점의 개수를 return 하도록 solution 함수를 완성해주세요.</p>

### 풀이

`n`, `m`이 최대 10<sup>9</sup>이라 가능한 시작점이 최대 10<sup>18</sup>개에 달하므로, `n × m`개의 시작점을 하나씩 정방향으로 시뮬레이션하는 것은 애초에 불가능하다. 대신 도착점 `(x, y)`에서 출발해 쿼리를 **거꾸로** 되짚으며, "이 쿼리들을 순서대로 거치면 결국 `(x, y)`에 도착하게 되는 시작점들의 범위"를 구하는 방식으로 접근한다.

1. 행을 바꾸는 쿼리(2, 3)와 열을 바꾸는 쿼리(0, 1)는 서로 완전히 독립적이므로, 2차원 좌표 전체를 추적할 필요 없이 행 범위 `[r_min, r_max]`와 열 범위 `[c_min, c_max]`를 따로 추적해도 된다.
2. `(x, y)`를 초기값으로 두고 `queries`를 뒤에서부터 순회하면서, 각 쿼리의 "역방향 이동"을 현재 범위에 적용해 범위를 넓혀간다. 예를 들어 원래 쿼리가 "오른쪽으로 `dx`" 였다면, 역으로는 "왼쪽으로 `dx`만큼 되돌린 시작 위치들"을 구해야 하므로 범위를 왼쪽으로 확장한다.
3. 문제는 격자 벽에 막혀 멈추는 클램핑(clamp) 처리다. 여러 시작 좌표가 벽에 부딪혀 전부 같은 좌표로 수렴할 수 있기 때문에, 역추적 시 현재 범위가 이미 벽(`0` 또는 `n-1`/`m-1`)에 닿아 있다면 그 경계는 그대로 두고(벽에 닿아 뭉개진 시작점들을 전부 포함), 벽에 닿아 있지 않다면 `dx`만큼 그대로 평행이동시켜 클리핑만 해준다. (`if c_min != 0: c_min += dx` 부분이 바로 이 처리)
4. 매 쿼리마다 범위가 역전(`r_min > r_max` 또는 `c_min > c_max`)되면 그 순간 도달 가능한 시작점이 없다는 뜻이므로 즉시 0을 반환해 불필요한 연산을 줄인다.
5. 모든 쿼리를 역추적한 뒤 남은 행 범위의 폭과 열 범위의 폭을 곱하면 정답이 된다. 전체 연산은 `queries` 길이에만 비례(`O(queries)`)하고 `n`, `m` 크기와는 무관하다.

### 생각

처음에는 격자가 크더라도 "일단 모든 시작점에 대해 시뮬레이션"하는 방식을 떠올렸지만, `n`, `m`이 각각 10<sup>9</sup>까지 가능해서 시작점 개수 자체가 계산 불가능한 수준이라는 걸 바로 알아채고 접근을 완전히 뒤집어야 한다고 판단함.

정방향으로 "시작점 하나 → 도착점 하나"를 확인하는 대신, 역방향으로 "도착점 하나 ← 시작점들의 범위"를 구하는 쪽으로 사고를 전환한 것이 핵심 아이디어였음. 좌표 하나하나가 아니라 구간(interval) 단위로 추적해도 되는 이유는, 이동이나 클램핑 연산이 구간의 연속성을 깨지 않기 때문 — 어떤 구간에 속한 좌표들은 같은 이동을 거쳐도 항상 하나의 연속된 구간으로 남는다는 성질을 이용함.

가장 헷갈렸던 부분은 벽에 막혀 멈추는 경우의 역추적이었음. 처음에는 단순히 매번 `dx`만큼 구간을 넓히면 된다고 생각했지만, 벽 근처에서는 서로 다른 여러 시작 좌표가 한 지점으로 뭉개지기 때문에 이걸 놓치면 시작점 개수를 과소 계산하게 된다는 것을 깨달음. 그래서 "현재 추적 중인 범위가 벽에 닿아 있는가"를 기준으로 케이스를 나눠서, 벽에 닿아 있으면 그 경계는 확장하지 않고 유지(이미 그쪽으로는 무한히 많은 시작점이 뭉쳐 있다고 보고), 닿아 있지 않으면 정상적으로 `dx`만큼 넓히는 방식으로 해결함. 또한 행/열 쿼리가 서로 영향을 주지 않는다는 점을 일찍 포착해서 문제를 두 개의 1차원 문제로 쪼갠 것도 구현을 훨씬 단순하게 만든 결정이었음.
